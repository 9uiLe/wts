# wts の設計

wts は、複数の開発作業を Git worktree に分け、それぞれの作業の開始、ブランチの積み重ね、更新、終了を管理する CLI である。worktree とブランチの操作には Git を直接使い、作業ディレクトリとブランチをまとめた「セッション」を管理単位とする。

独立した作業には別のセッションを作り、一つの作業を段階的に進める場合は同じセッションにブランチを積み重ねる。wts は作業場所と Git の状態を管理し、編集、ビルド、テスト、PR の作成・マージ、エージェントの起動は利用者の開発環境で行う。

本書は開発者向けに、状態の所有者、操作の前提と結果、失敗時の復旧に必要な契約を定義する。コマンドの使い方は [README](../README.md)、設定と命名スクリプトの形式は [設定資料](configuration.md)、端末との通信は [CLI 入出力と hamio の連携](hamio.md)に定義する。

## セッションと管理範囲

Git worktree は、同じリポジトリの履歴とブランチを共有する別々の作業ディレクトリである。clone した元のディレクトリをメインチェックアウトと呼ぶ。メインチェックアウトの位置は、そこでチェックアウトしているブランチ名とは無関係に決まる。

一つのセッションは、`start` が作る worktree、その最初のブランチであるルートブランチ、ルートに続くスタックブランチから成る。各 worktree でファイルを編集できる一方、ブランチ参照はリポジトリ全体で共有する。並列作業では別々のブランチ名と作成先を使う。

ルートのスタック番号は `1` とする。後続ブランチは `<root>-pr<n>-<名前>` の形式で、`stack` は未使用の `2` 以上の番号を使って作成する。例えば `login` に続くブランチは `login-pr2-validation` となる。番号はセッション内の順序であり、GitHub の PR 番号とは独立している。

管理範囲は、設定の `worktreeDirectory` の子孫ディレクトリである。指定したディレクトリ自体、メインチェックアウト、Git の管理領域はセッションの作成先にしない。相対の管理範囲はメインチェックアウトを基準に解決し、実行する worktree によって配置先が変わらないようにする。

セッションの所属は、Git に登録された worktree のパス、保存したルートブランチ名、その操作で取得したローカル参照から求める。ルートは存在するローカルブランチとし、`HEAD`、先頭が `-` または `@{` の値を認めない。識別情報を読めない場合やルートが存在しない場合、`list` は「未管理」と表示し、`stack`・`restack`・`discard` は操作を拒否する。

## 状態の所有者と保存先

コミット、ブランチ、worktree の登録情報は Git が管理する。wts は操作に必要な設定と記録を次の場所に保存する。

| 状態 | 保存場所 | 用途 |
| --- | --- | --- |
| プロジェクト設定 | `.wts.json` | ベースブランチ、管理範囲、命名規則の共有 |
| セッション識別情報 | worktree 専用 Git ディレクトリの `wts-session.json` | `rootBranch` によるルートの特定 |
| restack の lease | worktree 専用 Git ディレクトリの `restack-lease` | rebase 開始前の origin のブランチ OID の保存 |
| コピー対象 | 実行元 worktree の `.worktree-copy` | コピーする管理外ファイルの相対パス・glob の指定 |

設定は実行元 worktree のルート、メインチェックアウトのルートの順に探索し、最初に見つかった一つを使う。複数の設定はマージしない。設定の検査は名前をオプションで指定した場合も行うため、設定済みスクリプトは実在する実行可能ファイルである必要がある。

OID は Git オブジェクトの識別子である。lease は、リモート参照の更新時に期待する OID を記録したものを指す。wts は削除や push の際に期待する OID と対象を照合し、別の作業による参照の更新を検出する。

所属ブランチの一覧と表示用の参照は永続化せず、各コマンドで取得する。ルートとブランチ名の形式から所属を求め、スタック番号順、同じ番号ではブランチ名順に扱う。

## 入力の解決と実行予定

各コマンドは、入力の解決、対象の検査、必要な確認、変更、結果表示を組み立てる。ベースブランチのオプション・環境変数・設定の優先順位は [ベースブランチ](configuration.md#ベースブランチ)に従う。`start` と `restack` のベース上書きは、`cleanup`・`discard` が保護する設定のベースを変更しない。

`start` のブランチ名と worktree 名は、それぞれ明示オプション、設定した命名スクリプト、既定名の順に解決する。ブランチ名を確定してから worktree 名を決めるため、worktree の命名には確定したブランチ名を使える。各入力と既定値は [名前の解決](configuration.md#名前の解決)に定義する。

命名スクリプトは、名前を明示していない側で設定されている場合だけ実行する。`--task` はそのスクリプトへ渡す作業内容であり、実行するスクリプトがある場合だけ、省略時に作業内容を質問する。非対話では必要な作業内容を `--task` で指定する。名前は入力元によらず同じ検査を通し、不正な名前、ブランチや作成先の衝突は拒否する。命名の失敗を既定名で補わない。

`--dry-run` は、その時点の入力と状態から実行予定を表示する。fetch、ブランチ・worktree の変更、コピー、セッション情報・lease の書き込み、push は行わない。予定の判断に必要な次の処理は実行する。

| 操作 | dry-run で行う処理 |
| --- | --- |
| `start`・`stack` | 名前の解決に使う命名スクリプトの実行 |
| `restack` | 通常モードでの origin の参照照会。`--push-only` は保存済み lease の読み取り |
| `cleanup` | GitHub のマージ済み PR と、取り込み判定に必要なリモート情報の照会 |
| `discard` | `--remote` 指定時の push 先の参照照会 |

命名スクリプト自身の通信や副作用は wts の抑止対象に含まれない。dry-run の結果は予約や承認済み計画として保存せず、本実行で入力と状態を解決し直す。

## セッションの作成とコピー

`start` はベース、ブランチ名、作成先、コピー元を確定し、名前・パスの衝突とコピー一覧を検査する。コピー一覧がなければ対象なしとし、存在する一覧を読めなければ worktree の作成を始めない。

通常実行では、ベースの取得、Git によるブランチと worktree の作成、セッション識別情報の記録、管理外ファイルのコピーの順に進む。`origin/` で始まるベースは fetch し、失敗時は警告して利用可能なローカル参照を使う。有効なベース参照がなければ作成を拒否する。

新しい worktree の追跡ファイルはベースのコミットから作る。呼び出し元の未コミット変更を一括で移す操作は行わず、ファイルの持ち込みは `.worktree-copy` の指定に従う。コピー元は、ベースをローカルブランチ名で指定した場合はその worktree、該当しなければメインチェックアウトとし、`--copy-from` で変更できる。

コピーは対象を走査してから配置する。symlink、特殊ファイル、`.git`、コピー元・配置先の境界外を拒否し、Git 管理情報への書き込みやディレクトリの循環を防ぐ。配置先は書き込み直前にも検査する。dry-run は同じ走査で拒否予定を表示し、本実行は拒否した項目を警告してスキップする。拒否項目があることだけではセッション作成全体を失敗にしない。

成功時はブランチと `Path` を返す。後続の編集やコマンドはその `Path` で実行する。wts は呼び出し元シェルのディレクトリを変更しない。作成後の失敗は自動で取り消さず、パスとブランチ、worktree と識別情報の作成済み範囲を報告する。

## スタックの更新と再開

`stack` はセッションの先端から新しいブランチを作り、同じ worktree でそのブランチへ切り替える。作業ツリーはクリーンであることを要求し、未使用のスタック番号と有効なブランチ名を確定してから作成する。

`restack` は、番号順の各ブランチが前のブランチの子孫となる線形スタックをベースへ rebase する。作業ツリーがクリーンでない場合、rebase が進行中の場合、所属ブランチが別の worktree で使用されている場合は拒否する。`stack` と `restack` のクリーン判定は、無視対象ファイルを除く未コミット変更と未追跡ファイルを対象とする。

通常モードは、ベースの解決と取得、origin のブランチ OID の照会、lease の保存、スタック先端での `rebase --update-refs`、push の順に進む。ベースの fetch 失敗時は警告してローカル参照を使うが、origin の lease を取得できなければ rebase を始めない。非対話の本実行では `--push` または `PUSH=1` を必須とし、未指定なら push 対象の有無にかかわらず fetch・lease 保存・rebase の前に拒否する。

rebase 後の参照が lease と異なるブランチを push 対象とする。push は期待する OID を明示した lease と atomic push を使うため、リモートの更新や一部の参照の拒否を検出すると一括の push を拒否する。

対話の push 確認は rebase 後に行う。否定・Ctrl-C は正常終了としてローカルの rebase 結果と lease を残す。競合や push 失敗でも lease を保持する。push 成功時、または push 対象がない場合は lease を除去する。rebase が進行中でなければ、終了時に元のチェックアウトへの復帰を試み、失敗は警告する。

`--push-only` は保存済み lease で push を再開する。ベース解決、fetch、rebase、リモート OID の取り直しを行わず、rebase 開始後の他者の更新を検出する比較基準を保つ。lease の欠落・不足は操作を拒否する。競合解消を含む手順は [rebase と push の再開](../README.md#rebase-と-push-の再開)に定義する。

## 並列操作と参照の照合

worktree は作業ファイルを分離するが、Git の参照は共有する。そのため、表示や計画で取得した状態を変更時まで不変とは扱わない。ローカルブランチの名前と OID は一回の `for-each-ref` で取得し、`refs/heads/` からの相対名で識別して同名タグとの混同を防ぐ。worktree のパス、現在のブランチ、ロック状態は worktree 一覧から取得する。

取得した一覧は一つの判定段階で再利用し、変更の前後で次の照合を行う。

| 操作 | 照合する状態 |
| --- | --- |
| `list` | 同じ参照一覧から全セッションの所属を求め、各 worktree の状態を調べる |
| `start`・`stack` | 作成する名前とパスの衝突。実作成時の競合は Git の失敗として扱う |
| `restack` | 実行前の所属・線形性・他 worktree での使用、rebase 後のローカル参照、push 時のリモート OID |
| `cleanup` | 分類時と削除直前のブランチ OID・worktree 対応、worktree 削除後のブランチ使用状況 |
| `discard` | 提示時と承認後の削除計画全体、各参照の削除時の OID |

OID 条件付きの参照更新と atomic push が原子性を保証する範囲は Git の参照である。worktree の検査から削除までを含む操作全体はトランザクションではなく、最終検査後に別プロセスがチェックアウトやファイルを変える競合まで排除しない。部分失敗では、完了した操作と残った状態を区別して報告する。

## マージ済みブランチの整理

`cleanup` は、マージ済み PR とローカル変更の取り込みを根拠に、ローカルブランチと対応する worktree を削除する。ローカルブランチ全体を走査し、設定のベース、実行中のブランチ、管理範囲外の worktree で使用中のブランチを除く。セッション識別情報は取り込みの証明には使わない。リモートブランチは削除しない。

判定には同じ GitHub リポジトリのマージ済み PR を使い、fork の PR を根拠にしない。通常実行は分類前に設定のベースを fetch するため、削除確認前にもリモート追跡参照が変わり得る。fetch 失敗時は警告してローカル参照で判定する。

取り込みは、PR の head OID との一致、ベースへの祖先関係、書き換え後のパッチ一致によって判断する。パッチ比較は末尾空白も含める。書き換え後の比較では、origin に残る同名ブランチ、未 push の tip、独自 merge commit、パッチの不一致、照会・比較の失敗を自動削除の拒否理由とする。

対象ブランチと worktree のパスを提示し、対話承認または `--yes` を受けて削除する。分類時の OID と対応関係を直前に照合し、変わった対象は削除しない。worktree は強制削除するため、未コミット変更、未追跡ファイル、無視対象ファイルも削除範囲に含まれる。残す内容の保全は実行前に必要となる。

worktree の削除に失敗した対象のブランチ参照は保持する。成功した対象はブランチの使用状況を再取得し、計画した OID を条件として参照を削除する。ブランチ設定は参照削除後に除去し、設定が存在しない場合も成功とする。

失敗は対象と段階ごとに記録し、完了件数、残存対象、手動操作を報告する。prune の失敗も報告し、設定だけが残った場合は「参照削除済み・設定残存」と示す。認証情報を含み得る外部診断はそのまま表示しない。

## セッションの破棄

`discard <path>` は、指定した一つのセッションをマージ状況にかかわらず破棄する。対象は登録済み worktree のルートパスとし、メイン、実行中、管理範囲外、未管理、ロック中の worktree は拒否する。現在のブランチがセッションに属さない場合や、所属ブランチに設定のベース・別 worktree で使用中のブランチが含まれる場合も拒否する。

削除計画は、worktree、ルート、現在のブランチと HEAD、所属ブランチと OID、dirty 状態を含む。dirty は未コミット変更、未追跡ファイル、無視対象ファイルを含み、`list` も同じ基準で破棄に `--force` が必要な状態を表示する。`--force` はこれらのファイルの破棄、`--yes` は確認入力の省略を指定する。承認後に計画を取得し直し、一致する場合だけ削除する。

`--remote` を指定した場合は、そのリモートの push 先にある同名ブランチと OID を計画へ含める。照会と削除には同じ push URL を使い、URL が複数のリモートは拒否する。Git の atomic push は複数の送信先をまたぐ削除を保証できないためである。`--remote` を指定しない操作では通信しない。

リモートで拒否された場合にローカルの作業と再実行手段を残すため、削除は次の順序で行う。各段階の成功を確認してから次へ進み、完了した段階は取り消さない。

| 段階 | 操作 | 失敗時に残る状態 |
| --- | --- | --- |
| リモート参照 | OID を明示した lease 付き atomic push で削除 | ローカルの worktree とブランチを保持。通信障害ではリモートの結果が不明な場合がある |
| worktree | `--force` の指定に応じて削除 | ローカルブランチを保持 |
| ローカル参照 | OID 条件付きトランザクションで削除 | worktree は削除済み。ブランチと設定を保持 |
| ブランチ設定 | 削除したブランチの設定を除去 | worktree と参照は削除済み。未処理の設定が残る |

結果には完了段階と残存対象を示す。認証情報を含み得る push URL とリモートの外部診断は表示しない。

## モジュールの責務

コマンドは操作の順序と復旧案内を担当し、Git、設定、ファイル操作、表示を次の境界に分ける。

| 境界 | 責務と主な実装 |
| --- | --- |
| コマンド | [cli.ts](../src/cli.ts) が引数・環境変数と終了コードを扱い、[commands/](../src/commands/) が前提検査・操作・結果表示を組み立てる |
| プロジェクトとセッション | [project.ts](../src/project.ts)・[config.ts](../src/config.ts) が位置と設定を解決する。[session.ts](../src/session.ts) が識別情報と取得済み参照から所属を求める |
| Git と GitHub | [git.ts](../src/git.ts)・[github.ts](../src/github.ts) が操作と照会結果を返す。表示や質問は行わない |
| 作成時の入力とファイル | [naming.ts](../src/naming.ts) が名前の生成・検査、[copy.ts](../src/copy.ts) がコピー対象の走査・検査・配置を担当する |
| 利用者との入出力 | [ui.ts](../src/ui.ts)・[prompts.ts](../src/prompts.ts) が表示と質問を組み立て、[display.ts](../src/display.ts) が要求を分割し、[hamio.ts](../src/hamio.ts) がプロトコルと子プロセスを管理する |
| 外部プロセス | [process.ts](../src/process.ts) が実行ファイル・引数配列・標準入出力を扱う |

セッションの読み取りは位置情報と取得済み参照を受け取り、Git を再実行せずに所属を返す。これにより、一覧取得と状態の解釈を分離し、照合に使った参照をコマンドから追えるようにする。

CLI 本体の外部プロセスは doctor と命名スクリプトを含め `process.ts` から起動する。外部入力をシェル文字列へ連結せず、引数配列または標準入力で渡す。外部 JSON は境界で構造と型を検査する。テスト用コマンドと開発スクリプトはこの実行経路の対象外である。

## 表示・対話・進捗

利用者への表示、質問、進捗は PATH 上の hamio v0.1.0 / API v1 が担当する。wts は操作を始める前に互換性を確認する。表示形式は `--format human|json` で指定し、省略時は stderr が TTY なら human、それ以外は json とする。

人向け表示は stderr、機械向け応答は stdout へ出力する。stdout は表示要求と進捗終了の応答を一行ずつ返す NDJSON であり、ヘルプ、バージョン、スキル取得も同じプロトコルを使う。複数の表示項目は意味のある単位でまとめ、項目数・block 数・バイト数の API 上限に収まる要求へ分割する。例えば `list` は worktree ごと、`discard` は計画の項目一覧をまとめて表示する。

対話には stdin・stderr 両方の TTY、`TERM` が `dumb` 以外、`CI` が未設定または空であることを要求する。`--format json` では対話せず、必要な入力がなければエラーとする。確認質問は否定を初期選択とし、テキスト入力では既定値や省略の選択を解決してから入力を求める。

時間のかかる外部操作は非同期で実行する。進捗プロセスは成功・失敗の両方で終了させ、結果表示や質問の前に端末を復元する。否定と Ctrl-C は正常終了とするが、確認までに完了した Git 操作は取り消さない。

hamio の `status: "ok"` は表示要求の処理成功を表す。操作の成否は wts の終了コードと診断で判断する。hamio を利用できない場合は wts が JSON エラーを stdout に返し、終了コードを `1` にする。操作と進捗終了の両方が失敗した場合は操作の例外を優先する。手動コマンドの案内では引数を安全に引用する。

プロトコル、フォーム一時ファイル、子プロセスの解放、表示上限の詳細は [hamio の連携契約](hamio.md)に定義する。

## インストーラー

Web・ローカルの両インストーラーは、バイナリ、SHA-256、`BUILD_INFO` を照合してから配置する。配置先に wts がある場合は symlink ではない通常ファイルであることを要求し、同じディレクトリの staging から検証済みの内容を rename する。検証・配置に失敗した場合は配置済みバイナリを保持する。

インストールはシェル設定、認証、Gatekeeper の設定を変更しない。成果物の構成、検証、公開条件は [開発資料](development.md)に定義する。

## 検証の対応

振る舞いは CLI の入口から、一時 Git リポジトリ、bare origin、テスト用の外部応答で検証する。並列作成では作業ツリーの分離、削除や push では確認の拒否・キャンセル・参照競合・途中失敗時の残存状態を確認する。

| 契約 | 主な検証先 |
| --- | --- |
| 名前の解決・同時作成・コピー・スタック作成 | [start.test.ts](../tests/start.test.ts)、[config-session.test.ts](../tests/config-session.test.ts) |
| 参照の識別・一覧表示 | [common.test.ts](../tests/common.test.ts)、[list.test.ts](../tests/list.test.ts) |
| rebase・lease・push | [restack.test.ts](../tests/restack.test.ts) |
| マージ判定・安全な整理 | [cleanup.test.ts](../tests/cleanup.test.ts) |
| 破棄の計画・確認・段階別失敗 | [discard.test.ts](../tests/discard.test.ts) |
| 入出力・上限・TTY | [ui.test.ts](../tests/ui.test.ts)、[terminal.test.ts](../tests/terminal.test.ts) |

性能は入力と実行環境を揃え、経過時間、外部プロセスの起動数、バイナリサイズ、OS が報告する最大 RSS を測定する。測定方法は [性能を比較する](development.md#性能を比較する)、変更ごとの必須検証は [検証を実行する](development.md#検証を実行する)に従う。
