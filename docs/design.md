# wts の設計

wts は、Git worktree と線形のブランチスタックをセッションとして管理する CLI である。本書は、開発者が操作の対象、状態の所有者、処理の順序、失敗時に残る状態を理解するための設計と安全契約を定義する。操作手順は [README](../README.md)、設定の形式は [設定資料](configuration.md)、端末との通信は [CLI 入出力と hamio の連携](hamio.md)を参照する。

## セッションと管理範囲

Git worktree は、同じリポジトリの履歴とブランチを共有しながら、別のディレクトリで作業するためのチェックアウトである。wts のセッションは、一つの worktree、ルートブランチ、そのルートに属するスタックブランチから成る。

ルートのスタック番号は `1` とする。`stack` は `<root>-pr<n>-<名前>` の形式で、未使用の `2` 以上の番号を持つブランチを作る。例えば、ルート `login` の次のブランチは `login-pr2-validation` となる。番号はスタック内の順序を表し、GitHub の PR 番号とは独立している。

管理範囲は設定の `worktreeDirectory` の子孫ディレクトリであり、指定したディレクトリ自体は含まない。ブランチとディレクトリは別々に命名できる。セッションへの所属は、Git に登録された worktree のパス、セッション識別情報、ローカルブランチの参照から判断する。

セッション識別情報には、存在するローカルのルートブランチを指定する。`HEAD`、先頭が `-` または `@{` の値はルートとして受け付けない。識別情報を読めない worktree やルートブランチが存在しない worktree は、`list` では未管理として表示し、`stack`・`restack`・`discard` では操作を拒否する。

## 状態の所有者と保存先

ブランチ、コミット、worktree の登録情報は Git が管理する。OID は Git オブジェクトの識別子であり、wts はブランチ先端のコミット OID を削除や push の競合検出に使う。wts が扱う設定と操作記録は次のファイルに保存する。

| 状態 | 保存場所 | 内容 |
| --- | --- | --- |
| プロジェクト設定 | `.wts.json` | ベースブランチ、worktree の管理範囲、命名規則 |
| セッション識別情報 | worktree 専用 Git ディレクトリの `wts-session.json` | `rootBranch` にルートブランチ名を保存 |
| restack の lease | 同じ Git ディレクトリの `restack-lease` | rebase 開始時点で取得した origin のブランチ OID |
| コピー対象 | 実行元 worktree の `.worktree-copy` | コピーする相対パスと glob |

lease は、リモート参照を更新するときに期待する OID の記録である。push 先の OID が記録と異なれば、その参照の更新を拒否する。`restack` はこの記録をファイルに保存し、競合解消や push の見送りを挟んだ再実行でも利用する。

一覧表示や削除計画に使う参照一覧は、コマンドの実行中だけメモリに保持する。セッションの所属ブランチは保存済みの一覧から復元するのではなく、その操作で取得したローカル参照とルートブランチ名から求める。

作業ツリーの dirty 判定は操作の目的で異なる。`list` と `discard` は未コミット変更、未追跡ファイル、無視対象ファイルを含め、破棄に `--force` が必要かを同じ基準で判断する。`stack` と `restack` が要求するクリーンな作業ツリーには、無視対象ファイルを含めない。

## モジュールの責務

コマンドが入力の解決、対象の検証、操作、結果表示を順に組み立てる。各モジュールは次の責務を持ち、処理順序と失敗時の状態をコマンドから追える構成とする。

| モジュール | 責務 |
| --- | --- |
| [`src/cli.ts`](../src/cli.ts) | Commander による引数・環境変数の解決、hamio の事前確認、終了コードとエラー表示 |
| [`src/commands/`](../src/commands/) | コマンドごとの前提条件、確認、操作順序、復旧案内 |
| [`src/project.ts`](../src/project.ts) | リポジトリの位置と設定の取得、ベースの解決、fetch の進捗・結果の扱い |
| [`src/config.ts`](../src/config.ts) | 設定の探索・読み取り・検証・初期化とパスの解決 |
| [`src/git.ts`](../src/git.ts) | Git コマンドの実行、ブランチ参照・worktree・作業ツリー状態の取得 |
| [`src/session.ts`](../src/session.ts) | セッション識別情報の読み書き、取得済み参照からの所属・順序の決定 |
| [`src/github.ts`](../src/github.ts) | GitHub CLI によるリポジトリ・PR・コミットの照会と応答検証 |
| [`src/naming.ts`](../src/naming.ts) | 既定の名前の生成、命名スクリプトとの通信、名前の検証 |
| [`src/copy.ts`](../src/copy.ts) | コピー一覧の読み取り、コピー対象の走査、安全検査、ファイルの配置 |
| [`src/ui.ts`](../src/ui.ts)・[`src/prompts.ts`](../src/prompts.ts) | 表示と進捗、質問の組み立て、否定・キャンセルの扱い |
| [`src/display.ts`](../src/display.ts) | 表示内容を API 上限内の要求へ分割する副作用のない計算 |
| [`src/hamio.ts`](../src/hamio.ts) | hamio の互換性確認、要求・応答の検証、対話・進捗プロセスの管理 |
| [`src/process.ts`](../src/process.ts) | 実行ファイルと引数配列による外部プロセスの起動、標準入出力の接続 |

Git と GitHub のモジュールは、照会結果を返し、表示や質問は行わない。セッションの読み取り関数 `readSession` は worktree と Git ディレクトリの位置、管理範囲、取得済み参照を受け取る。識別情報ファイルを読み、Git コマンドを実行せずにルートと所属ブランチを返す。セッションの記録処理は、作成した worktree の Git ディレクトリを調べて識別情報を書き込む。

CLI 本体の外部プロセスは、doctor と命名スクリプトを含めて `process.ts` から起動する。外部入力をシェル文字列へ連結せず、引数配列または標準入力で渡す。外部 JSON は `unknown` として受け、使用する構造と型を各境界で検証する。テスト用コマンドと開発スクリプトは、この実行経路の対象外である。

## 参照の取得と操作前の照合

`localBranches` は一回の `for-each-ref` でローカルブランチの名前と OID を取得する。名前には `refs/heads/` からの相対名を使い、同名タグが存在しても対象のローカルブランチを識別できる。セッション内のブランチはルート名と命名形式で選び、スタック番号順、同じ番号ではブランチ名順に並べる。

worktree のパス、チェックアウト中のブランチ、ロック状態は、一回の worktree 一覧から取得する。パスの包含関係だけでは操作を許可せず、管理範囲のルート除外、セッション識別情報、操作に必要な symlink・権限・使用状況の検査を行う。

取得した情報を再利用できる期間は、コマンドの判定段階で区切る。Git や他のプロセスが参照を変更し得るため、次の時点で情報を取得する。

| 操作 | 取得と照合の時点 |
| --- | --- |
| `list` | 全セッションの所属判定に同じローカル参照一覧を使い、各 worktree の作業ツリー状態を調べる |
| `stack` | 識別情報と参照一覧からスタック先端と使用済み番号を求め、作成する名前の衝突を調べる |
| `restack` | 実行前に所属・線形性・他 worktree での使用を検査し、rebase 後にローカル参照を取得して push 対象を選ぶ |
| `cleanup` | 分類時の名前・OID・worktree を計画に保持し、削除直前に現在の対応と照合する。worktree 削除後もブランチの使用状況を調べる |
| `discard` | 提示用の計画と承認後に取得した計画を比較し、一致する場合だけ削除する |

取得済み情報は他のコマンド実行へ持ち越さない。OID 条件付きの参照更新と atomic push が守る範囲は Git の参照であり、worktree の検査から削除までを含む一連の操作全体はトランザクションではない。

## 実行予定の確認

`--dry-run` は、wts による fetch、ブランチ・worktree・コピー先・セッション情報・lease の変更、および push を抑止する。実行予定を判断するための PR 情報・リモート参照の照会と、設定した命名スクリプトの実行は行う。命名スクリプト自身の副作用は wts の抑止対象に含まれない。

## セッションの作成とコピー

`start` は、ベース、ブランチ名、worktree 名、既存のブランチ・パスとの衝突を検査し、コピー一覧を読み取る。コピー一覧がなければコピー対象なしとし、存在する一覧を読めなければ worktree の作成を開始しない。

ブランチ名と worktree 名はそれぞれ明示オプション、設定した命名スクリプト、既定名の順で解決する。明示名にも生成名と同じ検査を適用し、命名スクリプトは未指定の側だけ実行する。作業内容の入力は、実行する命名スクリプトがある場合だけ要求する。

通常実行は、ベースの取得、worktree とブランチの作成、セッション識別情報の記録、管理外ファイルのコピーの順に進む。origin のベース取得に失敗した場合は警告し、利用可能なローカル参照を使う。作成後に失敗した場合は自動で取り消さず、Path、ブランチ、worktree と識別情報の作成済み範囲を報告する。

コピーは、書き込みを行わない走査で対象を調べてから配置する。symlink、特殊ファイル、`.git`、コピー元・配置先の境界外を拒否し、worktree 外や Git 管理情報への書き込み、ディレクトリの循環を防ぐ。配置先は書き込み直前にも検査する。

dry-run と本実行は同じ走査を使う。dry-run は拒否予定を表示し、本実行は拒否した項目を警告してスキップする。拒否対象があることだけを理由に、セッション作成全体を失敗にはしない。

`stack` は、管理対象のセッション内で、クリーンな作業ツリーとスタック先端から実行する。未使用のスタック番号と有効なブランチ名を確定してから、そのブランチを作成してチェックアウトする。

## スタックの更新と再開

`restack` は、番号順の各ブランチが前のブランチの子孫となる線形スタックを対象とする。所属ブランチが他の worktree で使用されている場合は拒否する。非対話での実変更には `--push` または `PUSH=1` を要求し、指定がなければ fetch・lease 保存・rebase の前に拒否する。push 対象がない場合も同じ条件を適用する。

通常実行では、ベースを解決・取得し、origin のブランチ OID を照会して lease に保存する。その後、スタック先端で `rebase --update-refs` を行い、ローカル参照を取得して lease と異なるブランチを push 対象に選ぶ。ベースの fetch に失敗した場合は警告し、利用可能なローカル参照を使う。

push は保存した OID を明示した lease と atomic push を使う。リモートの更新を検出した場合や、複数の対象の一部を更新できない場合は、一括の push を拒否する。リモート照会の失敗や lease の不足も push を中止する条件である。

対話での push 確認は rebase 後に行う。否定・Ctrl-C は正常終了とし、rebase 後のローカル参照と lease を残す。push が成功した場合、または push 対象がない場合は lease を除去する。rebase が進行中でなければ、終了時に元のチェックアウトへ復帰する。

`--push-only` は保存済み lease を使って push を再開する。ベース解決、fetch、rebase、リモート OID の再取得は行わない。rebase 開始後の他者の更新を検出するため、比較基準は保存した lease とする。競合解消を含む手順は [rebase と push の再開](../README.md#rebase-と-push-の再開)に記載する。

## マージ済みブランチの整理

`cleanup` は、同じ GitHub リポジトリでマージされた PR と、ローカル変更の取り込みを根拠に削除候補を分類する。設定のベース、実行中ブランチ、管理範囲外の worktree で使用中のブランチは候補から除く。fork の PR は削除の根拠に使わない。セッション識別情報の有無は、取り込みの証明にはならない。

通常実行では分類前に設定のベースを fetch するため、削除を承認する前にもリモート追跡参照が変わり得る。fetch に失敗した場合は警告し、ローカルにある参照で判定する。変更の取り込みは、PR の head OID との一致、ベースへの祖先関係、書き換え後のパッチ一致によって判断する。

パッチ比較には末尾空白も含める。書き換え後の比較では、origin にブランチが残っていること、未 push の tip、独自 merge commit、パッチの不一致、照会・比較の失敗を、自動削除の拒否理由として扱う。

削除対象のブランチ名と worktree のパスを提示し、対話承認または `--yes` を受けて処理する。OID は計画内に保持し、削除直前に現在の状態と照合する。分類時から対応が変わった対象は削除しない。worktree は強制削除するため、承認した対象の未コミット変更と管理外ファイルは残らない。

worktree の削除に失敗した場合は、そのブランチ参照を残す。削除に成功した場合はブランチの使用状況を再取得し、計画した OID を条件に参照を原子的に削除する。ブランチ設定は、参照削除に成功したものだけを除去し、設定が存在しない場合も成功として扱う。

失敗は対象、パス、段階ごとに記録し、完了件数、残存対象、手動操作を報告する。prune の失敗も個別に報告し、設定の除去に失敗した場合は「参照削除済み・設定残存」と示す。認証情報を含み得る外部診断は、そのまま表示しない。

OID の照合と参照削除は原子的に行う。worktree の最終検査後に別プロセスがチェックアウトを変更する競合まで、排除する保証は設けない。

## セッションの破棄

`discard` は、利用者がパスで指定したセッションを、マージ状況にかかわらず破棄する。メイン、実行中、管理範囲外、未管理、ロック中の worktree は削除できない。所属するブランチにベースブランチや別 worktree で使用中のブランチが含まれる場合も拒否する。

削除計画には、worktree、ルート、チェックアウト中のブランチ、HEAD、所属ブランチと OID、dirty 状態を含める。`--remote` を指定した場合は、その push 先にある同名ブランチと OID も記録する。リモートの照会先と削除先には、同じ push URL を使う。

リモートの push URL は一つに限定する。Git の atomic push は複数の送信先をまたぐ削除を保証できないため、複数 URL を持つリモートは拒否する。`--remote` を指定しない操作では通信しない。

dirty なファイルの破棄には `--force`、確認の省略には `--yes` を要求する。承認後に計画全体を取得し直し、提示した計画と一致する場合だけ削除する。各段階の成功を確認してから次へ進む。

| 段階 | 操作 | 失敗時に残る状態 |
| --- | --- | --- |
| リモート参照 | OID を明示した lease 付き atomic push で削除 | ローカルの worktree とブランチを保持。通信障害ではリモートの結果が不明な場合がある |
| worktree | `--force` の指定に応じて削除 | ローカルブランチを保持。完了したリモート削除は取り消さない |
| ローカル参照 | OID 条件付きトランザクションで削除 | worktree は削除済み。ブランチと設定を保持 |
| ブランチ設定 | 削除したブランチの設定を除去 | worktree と参照は削除済み。未処理の設定が残る |

リモートで拒否されたときにローカルの作業と再実行手段を残すため、リモート処理を先に行う。認証情報を含み得る push URL とリモートの外部診断は表示しない。

## 表示・対話・進捗

利用者への表示、質問、進捗は PATH 上の hamio v0.1.0 / API v1 が担当する。wts は業務処理を始める前に hamio の互換性を確認する。表示形式は全コマンド共通の `--format human|json` で指定し、省略時は stderr が TTY なら human、それ以外は json とする。

人向けの表示先は stderr、機械向け応答の出力先は stdout とする。stdout は、表示要求と進捗終了の応答を一行ずつ出力する NDJSON である。表示要求は複数の block と項目を含み、`display.ts` が API の項目数・block 数・バイト数の上限に収まる単位へ分割する。`ui.ts` は各要求を順番に処理する。

`list` は worktree ごと、`discard` は削除計画の項目一覧を一つの表示単位にまとめる。表示内容の組み立てと分割は、hamio の起動や端末操作から独立した処理とする。ヘルプ、バージョン、スキル取得も同じ出力プロトコルを使う。

対話には stdin と stderr の両方が TTY であること、`TERM` が `dumb` 以外であること、`CI` が未設定または空であることを要求する。`--format json` では対話しない。必要な入力がなければエラーとし、確認質問の初期選択は否定とする。既定値や省略の選択を解決してから、必要なテキスト入力を求める。

時間のかかる外部操作は非同期に実行する。進捗プロセスは成功・失敗の両方で終了させ、結果表示と質問の前に端末を復元する。否定と Ctrl-C は正常終了として扱うが、その時点までに完了した Git 操作を取り消すものではない。

hamio の `status: "ok"` は表示要求の処理成功を表す。業務操作の結果は wts の終了コードと診断で判断する。hamio を利用できない場合は wts が JSON エラーを stdout に返し、終了コードを `1` にする。業務処理が例外で終了し、進捗の終了処理も失敗した場合は、呼び出し元へ業務処理の例外を返す。手動操作の案内では、引数を安全に引用する。

要求と応答、フォーム一時ファイル、子プロセスの解放、表示上限の詳細は [CLI 入出力と hamio の連携](hamio.md)に定義する。

## インストーラー

Web・ローカルの両インストーラーは、バイナリ、SHA-256、BUILD_INFO を照合してから配置する。配置先に wts が存在する場合は、symlink ではない通常ファイルであることを要求する。配置先と同じディレクトリに staging を作り、検証済みの内容を rename する。検証・配置に失敗した場合は、既存のバイナリを保持する。

インストールはシェル設定、認証、Gatekeeper の設定を変更しない。成果物の構成、検証方法、公開条件は [開発資料](development.md)に定義する。

## 検証の対応

主要な振る舞いは CLI の入口から、一時 Git リポジトリ、bare origin、疑似外部応答を使って検証する。削除や push では成功だけでなく、確認の拒否、キャンセル、参照の競合、処理途中の失敗と残存状態を確認する。

| 契約 | 主な検証先 |
| --- | --- |
| セッション作成・コピー・スタック作成 | [start.test.ts](../tests/start.test.ts)、[config-session.test.ts](../tests/config-session.test.ts) |
| 参照の識別・一覧表示 | [common.test.ts](../tests/common.test.ts)、[list.test.ts](../tests/list.test.ts) |
