# 設計判断の記録

wts の設計と運用における選択理由を記録する。利用方法は [README](../README.md)、設定の契約は [設定資料](configuration.md)、責務と不変条件は [設計書](design.md)、開発・公開操作は [開発資料](development.md) に定義する。

## セッションの識別と命名

日常的に繰り返す操作を端末から指定しやすくするため、セッションの公開コマンドを `start`、`stack`、`cleanup`、`restack` とする。

命名に外部サービスの利用契約や認証を要求しないよう、既定名を日付＋UUID とする。プロジェクト固有の規則や AI による命名は、利用者が指定するスクリプトに委ねる。wts に特定のモデルやプロンプトを組み込まず、設定したプロンプトを JSON 標準入力で渡すことで、シェルの解釈を介さず任意の文章を扱えるようにする。明示した命名規則を満たせないまま作成を進めないよう、スクリプトの失敗は操作の中止とする。

ブランチとディレクトリには別の命名規則を適用できるよう、セッションのルートブランチを Git 管理領域へ記録する。セッションの識別をパスの名前から独立させ、手作業で作った worktree を誤ってスタック操作の対象にしない。

## プロジェクト設定の共有

プロジェクトのベースブランチ、作成先、命名規則をファイルで確認・共有できるよう、セッション操作には `.wts.json` を必須とし、`init` を初期設定の入口にする。既存ファイルは上書きせず、設定の編集内容を保護する。設定をコミットする運用により、ベースブランチから作る worktree へ設定を引き継ぎ、設定ファイルが未追跡のためスタック操作のクリーン条件を満たせない状態を避ける。

worktree ごとの設定を使いつつ、設定ファイルを各 worktree に複製せず利用できるよう、実行中の worktree を優先し、メインチェックアウトを次の探索先とする。どのファイルが操作を決定したかを明確にするため、複数の設定をマージしない。

作成先の相対パスをメインチェックアウト基準にすることで、実行する worktree によって管理範囲が変わらないようにする。スクリプトの相対パスは設定ファイル基準にし、設定とスクリプトを一緒に管理できるようにする。

設定検査ではスクリプトを実行しない。パスや実行権限の確認を、AI の応答・ネットワーク・任意の副作用に依存せず行えるようにする。実際の入出力検証は命名を実行する時点で行う。

## ベースブランチと操作時の選択

ベースブランチをプロジェクトの方針として共有するため、`.wts.json` の `baseBranch` はローカルブランチ名を表す。cleanup で保護する名前と、origin 上で取り込みを判定する参照を同じ設定から導出する。start・restack にもその参照を使い、セッションの作成・更新・整理の基準を揃える。設定ファイルにリモート参照を格納しないことで、保護対象と取り込み先の別々の設定が食い違うことを避ける。

start・restack は操作ごとにベースを選べるよう、オプションと環境変数を設定より優先する。いずれの指定もなければ `origin/main` を初期値とする対話で選択する。cleanup はプロジェクトの保護方針を使う操作であるため、設定だけからベースを決め、省略時は `main` とする。`init` はベースの選択を行わず、作成先と命名の設定を生成する。対話を省いてプロジェクト共通のベースを使う場合は、`baseBranch` を明示する。

このリポジトリでは `baseBranch` を `master` としてソースとともに管理する。開発者が作成・更新・整理のたびに指定する必要をなくし、ベースのコミットから作る worktree にソースと設定の両方を引き継ぐ。開発中のソースを実行する入口は `scripts/dev.sh` とし、配布バイナリのインストールを開発開始の条件にしない。

## Git 操作とデータの保護

管理外ファイルのコピーでは、worktree 外や Git 管理情報への書き込みとディレクトリの循環を防ぐため、パスの境界を検査し、シンボリックリンクを拒否する。

cleanup ではブランチ名だけを削除根拠にせず、マージ済み PR とローカル変更の取り込みを確認する。restack では、rebase と push の間に他者が更新したリモートを上書きしないよう、rebase 開始時の OID を保存し、明示的な lease と atomic push を用いる。リモート確認や保存情報に不足がある場合は push を中止する。

未マージの作業を破棄する場合は、マージを証明して整理する cleanup と判断根拠が異なるため、対象を明示する discard を提供する。worktree とスタックは一つのセッションとして管理するため、一式を表示して確認する。確認の省略と未保存ファイルの破棄を別オプションにし、非対話実行の指定だけでファイルを失わないようにする。

## 導入と環境検査

配布 CLI の起動確認を外部サービスの認証に依存させないため、`doctor` の実行情報表示と `doctor --check` の依存・認証検査を分ける。認証検査は成否だけを表示し、認証コマンドが返す情報をログへ転載しない。

導入経路を選べるよう、GitHub Releases から取得する Web インストーラーと、取得済みの成果物を配置するローカルインストーラーを用意する。Web インストーラーは単独で配信できる構成とし、Git・gh の導入や認証を要求せず wts を配置できるようにする。ローカルインストーラーでは、`--with-deps` を明示した場合に Homebrew の管理機能で Git・gh を導入する。成果物の検証と依存導入が成功してから配置し、検証失敗時に利用中の実行ファイルを置き換えない。

インストールからコマンド実行へ進めるよう、Web インストーラーの完了表示に PATH 設定と動作確認をまとめる。呼び出し元シェルの環境は子プロセスから変更できず、シェル設定には既存の編集内容があるため、自動編集は行わずコピーして実行できるコマンドを表示する。macOS の zsh を案内対象とし、配置先が既に PATH にある場合は設定案内を省く。

## 端末 UI

操作対象、実行予定、完了結果、警告を一貫した階層で伝えるため、コマンドの表示を共通 UI に集約する。色に依存せず意味を読み取れる文言を使い、対話のキャンセルや対象がない場合も結果を明示する。作成先と次の操作を示すことで、利用者が続けて作業できるようにする。非対話のログには見出しや装飾を出さず、対象を識別するキー値行と終了コードを使用する。

Chalk は出力先ごとの配色、Ora は処理中の進捗、Clack は入力と確認を担当する。入力と結果表示の責務を分け、確認後のメッセージは共通 UI から出す。外部処理は非同期に実行し、待機中も進捗の描画と端末入力を処理できるようにする。

Chalk `5.6.2` は Ora `9.4.1` が要求する `^5.6.2` と同じバージョン系列を使用し、重複導入を避ける。採用バージョンと推移的依存は `bun.lock` に固定する。公開元・ライセンス・スクリプト・既知の脆弱性は [依存の検証](development.md#依存の検証)に従って確認し、監査日時と結果を成果物に記録する。

## 端末 UI のレビュー

担当者が実行環境を用意せずコマンドの表示を確認できるよう、シナリオから実 CLI を実行し、画面と操作機能を含む静的 HTML を生成する。全件一覧は表示の一貫性を、変更一覧は採用済みの表示との差分を確認するために使う。件数、検索、コマンド絞り込みにより確認対象を選べるようにする。

比較の基準は採用した表示を表す Git 管理の収録 JSON とする。担当者による採用を明確にするため、基準版は明示的に更新し、UI と同じ変更単位で管理する。変更のないケースは一つの出力で示し、比較を必要とするケースに変更前後を並べることで、確認すべき差分を読み取れるようにする。

日付・UUID・一時パスや進捗の更新回数は表示の設計と独立して変わるため、比較から除外する。文言・色・対話・終了コードは比較対象とする。Git のリモートはローカル bare リポジトリ、GitHub 応答と障害はテスト用コマンドで再現し、表示の検証を実サービスの状態から独立させる。

レビュー画面は表示の判断に必要な情報に絞る。実行結果の調査に使う JSON と収録範囲の Markdown は専用ファイルとして保存し、HTML とともに CI のアーティファクトで共有する。未実測の条件は収録範囲で明示する。

## 開発環境と成果物

利用者と CI が同じ手順で開発環境を使えるよう、セットアップ・依存取得・実行・設定検査・ビルド・検査・配置を独立したスクリプトとして提供する。開発用の入口は固定 Nix 環境を選択し、配置用の入口は配布バイナリだけを使う環境でも実行できるよう macOS の標準コマンドを使用する。

バイナリ・SHA-256・`BUILD_INFO` の検証条件を一箇所で管理し、ビルド・検査・配置の間で条件がずれないようにする。外部コマンドやサービスに関係するテストは一時環境とテスト用応答を使い、検証のために利用者の認証やシステムを変更しない。

## 配布とバージョン

最低対応 macOS と Developer ID 署名・公証の方針が未確定のため、自動公開の対象は検証用 Pre-release とする。Apple Silicon macOS 上で生成バイナリを実行し、配布対象のアーキテクチャで起動できることを公開の前提とする。ダウンロード後の Gatekeeper の検証は別に扱う。

公開元コミットと成果物の対応を保つため、公開バージョンは追跡ファイルを書き換えずにビルド時に埋め込む。実行時のバージョン表示と公開用入力の検証は、それぞれ CLI と開発スクリプトの責務とする。

## GitHub でのインストーラー配信

リポジトリの clone や開発環境を導入の前提にせず、GitHub の公開リポジトリで配布を完結させるため、単独で実行できるシェルスクリプトを Pages、配布バイナリを Releases に置く。Pages の標準 HTTPS ドメインと Actions の標準ランナーを使用し、外部サーバーや独自ドメインを必要としない。

Pre-release を既定の導入対象にでき、利用者ごとの GitHub REST API 呼び出しを避けられるよう、配布対象タグを Pages の `channel.txt` で明示する。バイナリ・SHA-256・`BUILD_INFO` が揃って公開される前に対象を切り替えないよう、Release 公開後に Pages を配信する。公開済み Release を作り直さず配信を復旧・変更できるよう、Pages だけの手動配信も提供する。

導入時に同じ Release の成果物を検証することで、転送中の破損やバージョン・ターゲットの不一致を検出する。配置を検証後に行い、取得や検証の失敗で既存の wts を置き換えない。

## AI 向けスキルと CLI の整合

AI が読む操作手順を実行対象の CLI と揃えるため、インストールする `SKILL.md` はガイド取得の入口とし、詳細な操作手順は実行中のバイナリから取得する。バイナリを更新すれば、インストール済みの入口からも更新後のガイドを参照できる。入口とガイドをともに埋め込むことで、スキル用の追加配布ファイルやダウンロード処理を不要にする。

AI ごとにスキルの読み込み先を選べるよう、親ディレクトリを `--path` で指定する方式とする。AI 製品の設定ファイルは変更しない。利用者による編集を保護するため、異なる内容の `SKILL.md` の置き換えは明示的な `--force` を要求し、他のファイルを保持する。
