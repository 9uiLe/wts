# 作業ログ

この文書は実装と運用方針の判断理由を記録する。操作手順は [README](../README.md) と [開発資料](development.md)、責務と振る舞いは [設計書](design.md) に定義する。

## 開発操作と成果物検証の判断根拠

利用者と CI が同じ手順で開発環境を使えるよう、セットアップ・依存取得・実行・ビルド・検査・配置を独立したスクリプトとして提供する。開発用の入口が固定 Nix 環境を選択し、配置用の入口は配布バイナリだけを利用する環境でも実行できるよう macOS の標準コマンドを使用する。

配布単位であるバイナリ・SHA-256・`BUILD_INFO` の検証条件を一箇所で管理し、ビルド・検査・配置の間で条件がずれないようにする。文書は利用者の導入手順、開発者の操作、実装の責務に分け、新規参加者がそれぞれの目的から参照できる構成とする。

## 配布とバージョン管理の判断根拠

最低対応 macOS と Developer ID 署名・公証の方針が未確定のため、自動公開の対象は検証用 Pre-release とする。Apple Silicon macOS 上で生成バイナリを実行し、配布対象のアーキテクチャで起動できることを公開の前提とする。

公開元コミットと成果物の対応を保つため、公開バージョンは追跡ファイルを書き換えずにビルド時に埋め込む。実行時のバージョン表示と公開用入力の検証は、それぞれ CLI と開発スクリプトの責務とする。

## Issue・PR とコミットの設計根拠

作業の着手とレビューでは、要求する成果とその検証方法を共通の判断基準とする。[Issue テンプレート](../.github/ISSUE_TEMPLATE/task.md) は、背景・課題・契約・検討事項・作業内容・受け入れ条件を整理し、担当者が実施する作業と判断を要する点を区別できる構成とする。

[PR テンプレート](../.github/PULL_REQUEST_TEMPLATE.md) は、契約に対する変更内容、CLI と配布への影響、検証結果をまとめる構成とする。関連する Issue を参照し、受け入れ条件に対する実施結果と未検証事項を示すことで、要求する成果がどこまで証明されているかを明確にする。

レビュー中に説明と差分を直接対応付けられるよう、変更内容はコミットハッシュ単位で示す。開発時から目的ごとにコミットを構成し、メッセージに変更内容と目的を記すことで、個々の変更を履歴から理解できるようにする。
